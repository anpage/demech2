# Working on the simulator's editions

This continues [CLAUDE.md](../CLAUDE.md), the project's working reference: a section named in quotes that isn't in this file ("Codegen Patterns", "Hand-written Assembly", "reccmp"…) is one of CLAUDE.md's ("VC++ 2.2" is [VC22.md](VC22.md)).

[EDITIONS.md](EDITIONS.md) is the record of the editions themselves (who built each and how, what each changed, every feature); this file is how to work on them: where their code and annotations go, the tools, and what each edition's build taught. [TARGETS.md](TARGETS.md) lists the targets.

## Other builds of the simulator (MW2MATROX, MW23DFX, MW2ATI, MW2S3, MW2POWERVR)

The 3D-card editions shipped their own `MW2.DLL`, built from the game's source as it stood when each was made (the ATI edition in April 1996, the S3 edition in July, the Matrox edition in August and the PowerVR edition in September, all before 1.1; the 3Dfx edition in October). Matrox's is the one built like 1.1 (`/Od`, VC++ 4.0); the ATI, S3, PowerVR and 3Dfx editions' are optimized builds (`__fastcall`, frame pointers omitted; VC++ 2.x, S3's 4.x). All five are targets ("The 3Dfx edition", "The ATI edition" and "The S3 and PowerVR editions" below).

- **Editions and features.** The build defines an edition's identity: nothing for 1.1, `MW2_ACCEL` for the accelerated (3D-card) editions, which share most of their changes to 1.1 (the float conversion, the 16-bit VFXA port, the A3D renderer interface and its clients, the graphics menu and the registry settings), and with it `MW2_MATROX` or `MW2_3DFX`. The code tests **features**, named for what they do (`MW2_FLOAT_SCALARS`, `MW2_A3D`, `MW2_KEY_COLOR`, `MW2_RES_800X600`, `MW2_PIXEL_FORMAT` 565 or 555), which `util/types.h` maps from the identity, one `#define` per feature with a line saying what it does: a new header of them would move code (its first inclusion counts as a symbol on 4.0 and 4.1), where `types.h` is already included. A feature is true of every edition that has it, so a site names the feature its code belongs to, and a block that mixes two is split, or the minor one nested inside. Where no binary separates two features both editions have (the float conversion and A3D), the attribution follows what the code does. The identity itself is tested only by an edition's own back end and what the shared code does for it (the MSI95 and Glide back ends, the Matrox edition's `SimMain` window handling), by an edition's own definition of a function, where one edition's source writes the same computation another way (`MW2_3DFX`'s red-first colour stores, `HorizonYAtX`'s float `y`), and by the artefacts of how an edition's source was laid out rather than what its game does: the fragments placed at another object's position, globals in `.data` in one edition and `.bss` in another (`inputmap.c`'s sinks), functions only 1.1's object has, declaration orders, the parentheses and flag forms only 2.2's folding sees, and the pragmas that reproduce a unit's flags. A difference a binary shows in a site both editions compile is a feature of the edition that has it: add it to the table. The A3D layer is the game's interface to one back end per card (see "The A3D layer"): the code that calls it is shared, the back end isn't. `accel/a3d.h` declares what both renderers implement under shared names (`A3D_DrawPolygon`, `A3D_DrawOutline`, `A3D_EdgeCrossing`, `A3D_SetPalette`, `A3D_map_polygon`), each edition's own entry points under its identity, and `A3D_PANE_WIPE`, the 3D view's pane wipe (the Matrox renderer's, VFX's for the 3Dfx edition). A unit that defines something before its first include can't test a feature there (`types.h` isn't in yet): such a switch is defined unconditionally and tested with the feature in the header (`FIXEDTRIG_FLOAT_SINE`). `docs/EDITIONS.md` is the record of the editions: who built each and how, what each changed, and, generated from that table and the sources, every feature with the editions that have it and the functions that test it. After changing the table, adding or moving a conditional that names a feature or an edition, or renaming a function that holds one, run `python tools/edition_sites.py --doc`; CI's `--check` fails on a feature without a comment above its `#define`, a feature nothing tests, a tested `MW2_` macro the table doesn't define, a branch no target compiles, and a stale document. A difference that lives in an edition's own definition of a function (`SimMain`) is documented in the comment above that definition, not in the table. What proves each site for each edition isn't in the document: the retail workflow publishes it with the progress reports (`EDITIONSITES.md` and `.json`, from the certify job's `--no-states --json` list and the three simulators' states), and the PR comment carries its count of sites no proven function covers.
- **Folders:** units only the accelerated editions build are in `MW2/src/accel` and `MW2/include/accel` (`floatmath.c`, `graphicsmenu.c`, `registry.c`, `queueface.c`, `texturepoly.c`, `vfx16.asm`; `a3d.h`, `vfx16.h`…); an edition's own are in its folder (`MW2/src/matrox`: `a3d.c`, the A3D back end over MSI95, and `msidraw.c`, the MSI display back end, with `MW2/include/matrox/colorkey.h`; `MW2/src/3dfx`: `a3d.c`, the A3D back end over Glide, and `glidedraw.c`, the Glide display back end).
- **Shared source, one annotation per target.** An MW2 function the Matrox build has too carries `// FUNCTION: MW2MATROX 0x…` under its MW2 line, and so do globals and the CRT entries in `MW2/library_msvc.h`.
- **`tools/port_annotations.py`** writes those annotations: it finds each annotated MW2 function in the other binary (byte for byte apart from relocations and outgoing branches, or with a consistent permutation of its `[ebp-N]` slots; a function placed by its neighbours also when only the operand order of its comparisons differs), places duplicates by their neighbours, drops matches whose calls disagree, maps globals through the relocations the matched functions share (by majority vote), and matches the CRT from 1.1's and the shell's. It skips markers that already have one for the target, so rerun it after decompiling MW2 functions: `python tools/port_annotations.py --from MW2 MW2.DLL --to MW2MATROX MW2_MATROX.DLL --dirs MW2 common --csv reccmp/mw2-vfx.csv:reccmp/mw2matrox-vfx.csv --library-from MW2SHELL MW2SHELL.DLL MW2SHELL/library_msvc.h --library-to MW2/library_msvc.h --write`.
- **What doesn't port:** functions the Matrox edition changed (a renderer that uses floats where 1.1 has fixed point: `g_mainEyepoint`, `g_probeDirections`), and globals only those functions use. Functions it placed in another order or object take a fragment (next item).
- **Data the editions placed elsewhere** moves to the unit that holds it in every edition. Globals at a unit's edge in 1.1 that an edition puts next to another unit were that neighbour's all along (`g_jumpJetDrag` and `g_slideSlope` start `mechclass.c`'s data in every edition, the collision colours `faceshade.c`'s, `g_temperature` and `g_hostileAtmosphere` end `environment.c`'s), and a block whose neighbours differ from edition to edition is a data-only object of its own (`cockpitlayouts.c`, the cockpit readout and map layouts split from `targeting.c`; `commandpoint2menu.c`, split from `commandmenu.c`), linked at each target's position. Their declarations stay in the headers that had them (a note says so there): moving a declaration to another header moved the code of about 50 units in each simulator.
- **Code the Matrox edition placed elsewhere goes in a fragment:** a `.c` file of the moved functions (and their data), self-contained (its own includes), that no target compiles on its own: the unit that holds it in 1.1 includes it at 1.1's position under `#ifndef MW2_ACCEL`, and the unit whose object holds it in the Matrox edition at that position under `#ifdef MW2_ACCEL` (an edition that places it elsewhere again takes its own macro). reccmp finds the functions by the fragment's line records either way. `cockpitpanels.c` (config.c's in 1.1, the end of staticmem.c's object in the Matrox edition, of targeting.c's in the 3Dfx edition), `normalizerotation.c` (clock.c's, transform.c's), and `ai.c`'s `aireset.c`, `aiattacker.c`, `aiprox.c` and `aidist.c`, which `ai.c` includes twice, at each target's position. An edition that has the fragment as an object of its own builds it as a unit at that object's place in its link order, and the includer leaves it out there (GBL's `cockpitpanels.c`; `faceprojection.c`, which 1.1's `objectanim.c` includes; and `clockmath.c`, `clock.c`'s tables, which includes `normalizerotation.c` in turn). An object the Matrox edition put together from several 1.1 units' functions, all rewritten, is a unit of its own in `MW2/src/accel` with the accelerated editions' versions (`floatmath.c`: the tables and trigonometry of `clock.c`, `fixedtrig.c`, `approxlen.c` and two functions of `shapegeom.c` and `fixedsqrt.c`); 1.1's stay in their units, under `#ifndef MW2_ACCEL` where the accelerated editions build the unit.
- **Code that differs goes in the shared files, behind its feature** (`#ifdef MW2_FLOAT_SCALARS`, with `#else` holding 1.1's). Member types switch in the headers (`Mech::m_heat` is a `MechFloat` in the Matrox edition), and `MW2/include/fixedfloat.h`'s `FIXED_TO_INT(x)` is 1.1's `x >> 16` and the Matrox edition's cast: a float member assigned to an integer converts by itself. The Matrox edition's code isn't a mechanical translation, though: the scaling moves (`DrawHeatBar` drops the `>> 16` of the eased level instead), sign tests read the float's sign bit (`test byte ptr [x+3], 0x80`), locals and parameters become floats, and non-zero tests compare `fabs(x)` with a constant. Declarations added to shared headers can shift other targets' code (next item); the inactive branches themselves don't.
- **Small differences stay inside one body; an edition's own version is a definition of its own.** Where the editions differ at a few statements, the function keeps one signature and one body, with the features' `#ifdef` branches inside it (`MechScalar` covers parameters whose type differs). Where an edition's version differs in its control flow or in more than a few statements, each version is a separate definition in the same unit, under its own branch, and each definition carries only the annotations of the targets that compile it: the 3Dfx edition's `SetGameResolution` and `ChooseArtResolution`, the Matrox edition's `JoystickPoll`, the accelerated editions' `DrawSkyAndGround` and `UpdateMech`, and each edition's `SimMain` and `SimWindowProc`. A definition is selected by the feature that makes it different, or, for an edition's whole version (`SimMain`), by the edition. reccmp, decomplint, certify, the witness search and `tools/edition.py` find each target's definition by its own markers (measured: every object byte-identical, every state unchanged). What doesn't work is one marker block above two definitions: reccmp finds a function by the line its body starts on, so a block naming targets that compile different branches loses the function for some of them ("Failed to find function symbol").
- **Text the compiler skips doesn't change code; declarations do.** Measured on all three simulator compilers (every C unit of MW2, MW2MATROX and MW23DFX, each function's bytes): blanking every inactive edition branch (about 9,300 lines), shifting every unit's line numbers, renaming the edition macros, and adding dead `#ifdef` text ahead of each unit change nothing. What moves code is the number of file-scope symbols declared ahead of a function (one `typedef` or one `extern` ahead of each MW2 unit changes the same 83 functions: the count, not the kind; a prototype, two symbols, changes 126) and the names of its locals. So an edition's code behind `#ifdef` costs the other targets nothing, while a declaration added to a shared header can move every unit that includes it: rerun `tools/witness.py --write` on those units. (An earlier note here blamed an inactive line in `aiweapons.c` for a change in `DecideAIFire`; it didn't reproduce.)
- **Stack slots:** 4.0's slot assignment differs from 4.1's, and as under 4.1 it depends on the whole unit, whose Matrox version declared other things: functions identical in both originals can be slot-permuted in either rebuild. A closed question, as for 4.1.
- **`tools/edition.py`** keeps the pairing of the two originals' functions and compares the rebuilt Matrox edition with its original up to entropy: `report` (the closest unannotated functions, with their diffs), `cmp`, `auto` (annotates what matches), `audit` (sorts the annotated functions below 100% by what's left, from a reccmp JSON report), `crt` (the Matrox edition's C runtime, from the rebuild's 4.0 LIBCMT), and the `MechScalar` edits. Its comparison masks addresses: a function that reads a different global than the Matrox edition's passes it, and only reccmp shows it. `--target MW23DFX` works on the 3Dfx edition instead ("The 3Dfx edition").
- **Link order:** `vc40/targets.cmake` lists MW2's units in the Matrox edition's object order, found from the functions and data they share. 1.1's units it has nothing of (the fixed-point helpers, `directdraw.c`, `texpoly.c`) aren't linked: an `/Od` object without `/Gy` is linked whole, called or not. The optimized editions leave them out too. `tools/check_units.py --target MW2MATROX` passes with no known findings.
- **Fixed point became float.** The accelerated editions' simulation values are `float` where 1.1's are 16.16 fixed point, at the same offsets (`MW2_FLOAT_SCALARS`; `docs/EDITIONS.md`, "What the accelerated editions changed"). It isn't a mechanical translation: see "Code that differs" above.
- **Optimized units.** The Matrox edition's renderer (`MW2/src/matrox/a3d.c`, `/Ox /G5 /Op`) and depth sort (`/Ox /Oa /Op`) are optimized where its other units have `/Od`; how the flags were found is in `docs/EDITIONS.md`. A source takes such flags through its `DEMECH2_OPTIMIZATION` property (a list of `cl` flags, set in `vc40/targets.cmake`), which replaces the `/Od` every other source gets (`cmake/decomp_flags.cmake`, `cmake/game_dll.cmake`), and reccmp compares its functions like any others. A source property set after the target must `APPEND` to `COMPILE_OPTIONS`, or it drops that `/Od`. When probing flags under zsh, split the variable (`${=flags}`): an unsplit `/$flags` reaches `cl` as one unknown option.
- **The 16-bit 2D primitives.** The accelerated editions' game code draws through a 16-bit port of VFXA (`MW2/src/accel/vfx16.asm`, a MASM unit (form 4) generated by `tools/asm2masm.py --target MW2MATROX`; what it replaces is in `docs/EDITIONS.md`). `MW2/include/accel/vfx16.h` declares its routines and, under `MW2_VFX16`, redirects the VFXA names to them: a drawing unit includes it after `vfxa.h`, behind `#ifdef MW2_VFX16`. Only the accelerated editions' ML builds assemble it, so it has no portable C.
- **A global in `.data` in one target and `.bss` in the other** takes a declaration per target, each with its own annotation, in an `#ifdef MW2_ACCEL`/`#else` pair (`inputmap.c`'s sinks). Not a macro for the initializer (`MechS32 g_x SINK_INIT;`): reccmp's parser takes the macro for the variable's name.

## The 3Dfx edition (MW23DFX)

The 3Dfx edition's simulator (`MW2_3DFX.DLL`, the Diamond Monster disc's `MW2.DLL`) is the Matrox edition's C built by VC++ 2.2 with optimization, drawing through Glide (`GLIDE.DLL`, Glide 1.x) and linking 3dfx's Texus texture library.

- **Flags:** `/Ox /Ow /G5 /Gr /Gy`, with `network.c`, `shots.c` and `mechreload.c` at `/Od` (still `/Gr`), and 2.2's single-threaded `LIBC` (`/ML`); what shows `/Ow` rather than `/Oa` is in `docs/EDITIONS.md`. `vc22/targets.cmake` sets `DEMECH2_OPTIMIZATION` on every other source, which the `vc22/` sub-project honours like the 4.x builds (`/Od` is a compile option there, not one of `CMAKE_<LANG>_FLAGS`).
- **`/Gy`:** every function is a COMDAT of its own, so the linker pads between functions with `int3`, inside an object as between objects. `0xCC` padding is no object boundary in this binary: the unit split can't be read from it, so `tools/check_units.py` checks only the order of the units' runs of code and data (`MW23DFX comdat` in `tools/check_units_expected.txt`).
- **`/Gr` makes `__fastcall` the default.** Every function declared without a convention takes its first two arguments in `ecx`/`edx` and is named `@Name@N`. So the declarations of routines written in assembly (`vfxa.h`, `vfx3d.h`, `vfxrend.h`, `ticks.h`, `sndunpack.h`, `accel/vfx16.h`, `palette.h`'s lookaside routines), of imported C APIs (`msi95.h`) and of callbacks the C runtime calls (`CompareStaticPools`) spell out `__cdecl`, which `compat.h` defines away on platforms without it; for the other targets it is the default already. A function called through a pointer takes the pointer type's parameters, used or not: the AI message handlers that ignore their last argument still pop it (`ret 4`; `AiMessageFalse`). A function called without a prototype is named by the arguments of the call, so the declaration and the definition must agree: `ReloadPlayerMech` takes four parameters, as its callers always passed (the 3Dfx edition's `ret 8` shows the two unused ones).
- **Texus (`3rdparty/texus`)**, 3dfx's texture library, is a static library the target links first (`3rdparty/texus/texus.cmake`: `__cdecl`, `/Ox /G5 /QIfdiv-`), under its own licence, with its changes between dated `demech2: begin change` / `end change` comments, like `3rdparty/vfx`'s. `MW2/library_texus.h` annotates it (`LIBRARY`, outside the game-code `--total`). Its headers stay verbatim: its register allocation depends on the symbols a file declares. Where it comes from and where it sits is in `docs/EDITIONS.md`.
- **Annotations come from the rebuild:** the optimized code can't be matched against 1.1's bytes, but the rebuild is byte-identical to the original wherever the source is right. `tools/port_annotations.py --rebuild` takes the rebuild as its source binary, names each marker block's symbol through the rebuild's map, and matches functions, globals and the CRT the usual way: `python tools/port_annotations.py --from REBUILD build/vc22/MW2_3DFX.dll --rebuild build/vc22/MW2_3DFX.map --rebuild-pdb build/vc22/MW2_3DFX.pdb --located-differing --after MW2 MW2MATROX --to MW23DFX MW2_3DFX.DLL --dirs MW2 common --library-to MW2/library_msvc.h --write` (with reccmp's environment: `--rebuild-pdb` reads the statics, which a LINK map leaves out, with reccmp's cvdump). The mapped globals' pointer tables then place what they point to: the data no matched code reads (menus, map layouts, transitions), the small functions found more than once (the input drivers' entry points), and with `--located-differing` the functions whose code differs there, which reccmp then scores. Rebuild every target afterwards (the line records move), drop the annotation of any global datacmp then reports and of any function that turns out to be another one (the DirectDraw refresh modes' entries point to the 3Dfx edition's own display back end), and leave out the tables that point to them. `reccmp/mw23dfx-vfx.csv` comes from `tools/vfx_names.py --target MW23DFX`. The VFX objects are laid out the same in every edition (but for the ATI edition's `VFX_flat_polygon` and `VFX_Gouraud_polygon`, an older version of the routines; otherwise only `VFX_polygon_render` and `VFX_polygon_clip_XY_and_render` differ: the Matrox edition doesn't set `ES` and reads `poly_vectors` through `CS`, the 3Dfx edition keeps 1.1's code: `VFXREND.ASM` selects the Matrox edition's with `MW2_VFXREND_CS_SEGMENT`, which ML gets, like every feature, from `cmake/editions.cmake`), so a VFX label the tool can't place is at its Matrox address plus the offset of the routines around it.
- **The renderer and the display back end** are `MW2/src/3dfx/a3d.c` and `MW2/src/3dfx/glidedraw.c` (what they do and where they sit: `docs/EDITIONS.md`). The renderer's `.bss` variables are `static` (their order is the object's), and 2.2 lays statics out in an order of its own: a pointer just past an array names a different neighbour on either side.
- **Data the 3Dfx edition changed** (found by datacmp) is listed in `docs/EDITIONS.md`. Its resource type tags are separate globals (see "Data" under VC++ 2.2).
- **Inline helpers.** The edition expands `FixedMul16`, `FixedDiv16`, `MulDiv64`, `HashName` and `DebugBreakpoint` in every caller (`/Ox` implies `/Ob1`), their arguments stored to the stack and reloaded by the `__asm` body: their headers define them `__inline` under `MW2_INLINE_HELPERS` (the table's one artefact: the edition's source, not its game), with the units' assembly, and the units compile nothing for this target. `MemCopy` and `MemSet` are C there (`memcpy`/`memset`, which `/Oi` expands), and `QueueFace` is unoptimized (`#pragma optimize("", off)`): a function that looks hopeless may be compiled differently from its unit.
- **Shared by default, so watch for divergence.** Most features of both accelerated editions are both editions' because nothing shows otherwise yet, not because the 3Dfx edition was checked there: `tools/edition_sites.py` lists the sites and whether each edition proves the function around them. The A3D interface's clients are shared on the strength of `SetFilterTextures`; the key color fills turned out to be the Matrox edition's only (the 3Dfx edition calls `grChromakeyMode` only to disable it). When a 3Dfx function doesn't match, suspect the shared features' code it compiles before the source shape, and when the binary shows the editions differ there, make the difference a feature of the edition that has it.
- **Pairing with `tools/edition.py --target MW23DFX`** (`tools/edition_3dfx.py`). Optimized code can't be paired with 1.1's or the Matrox edition's bytes, so a source function without a MW23DFX annotation is paired with the original's unannotated function whose references are most like its rebuilt version's: the functions, imports and annotated globals it calls or addresses, and its strings (weighted). Functions with too few references are placed by their neighbours. `state` computes the pairing, `report` lists the pairs closest first with two ratios (as they are, and with the registers renamed away: a pair at 1.000 without registers differs only in register allocation), `cmp NAME` shows one, `auto` annotates the exact matches (`--registers`: also the register-only ones, with a comment saying so), `unpaired` lists the original's functions nothing paired, and `functions` counts the game code's functions (the `--total`) and lists the starts without an annotation: it traces the code from the annotations, the call targets it reaches and the `int3`-padded starts no traced code covers (an `0xCC` byte can be the low byte of an operand: `[0x1024e1cc]`, `g_eyepoint`), following branches and jump tables, adds the code only pointers reach (callbacks and table entries, after padding, a `ret`, a `ret N` or a `jmp`: `AiMessageDist`, `SampleEosCallback`), and leaves out the data annotated in `.text` (VFX's tables) and code off the 16-byte alignment every `/Gy` function has that only the function enclosing it points to (`SimMain`'s exception handler, `VFX_map_polygon`'s span routines). Every function Ghidra finds is among them but ten it splits after a `nop` inside a prologue (`LerpPaneRect`). reccmp scores them all: `GetJoystickDeviceCount`, a lone `jmp` to its import, looks like an import thunk, which our fork of reccmp leaves alone once an annotation has matched it. Rerun `state` after annotating: the new names pair more. Each annotation adds names, so a pass often lifts functions already annotated (their callees become named). `names REPORT.json` (a reccmp `--json` report) does that on purpose: it finds the annotated functions that differ only in operands the original's side can't name (`<OFFSETn>`), reads the addresses those operands hold in the original, and with `--write` annotates the source functions at them (`--all`: also the names in functions that differ otherwise), using a name only when every site agrees on its address and no other name claims it; it lists the globals and the C runtime's names it leaves to annotate by hand. Rebuild and rerun it until it finds nothing: named callees name their own callees. A function the edition places out of its file's order is annotated by name in its unit's header (`gifsave.h`, `wtbshapes.h`): the linter's order rule skips by-name markers, and `add_annotation` falls back to that block itself.
- **2.2's float folding.** Under `/Ox`, 2.2 folds and reassociates float constants: `x / 15.0f * 362.0f` becomes one multiply, `a * b / c` divides first, and `c - x / k` becomes `x * -1/k + c`. Where the original keeps the operations apart, parentheses or a cast stop it (`(p_level / 15.0f) * 362.0f`, `((a) * b) / c`, `3 * (x / k)`, `c - (MechFloat) (x / k)`), and at `/Od` they compile exactly like the plain expression, so 1.1's and the Matrox edition's code doesn't change (`fadepal.c`, `ramp.c`, `debris.c`, `mechcollision.c`, `GetApproachThrottle`).
- **Toggles are `x = !x`.** The original computes them without a branch (`cmp x, 1; sbb eax, eax; neg eax`); at `/Od` `x = !x` and `if (!x) { x = 1; } else { x = 0; }` compile identically, so the sources write `!x`. Likewise a flag set from a comparison is `x = a < b` (`setl`).
- **A store to a struct member may alias a struct pointer; a store to a scalar global doesn't.** Under `/Ox`, 2.2 and 4.1 assume that a store to a member of a struct global may change what a struct pointer reaches, and not that a store to a plain global may. So an original that reloads `p->m_x` after storing to an apparently separate global, or does a store through `p` before that global's store where the source has it after, stores to a member of a struct: `g_shapeOwner` (`ShapeOwner`: the set flag, the kind and the owner, three scalars until `LoadStaticObject` showed both in every optimized edition; probes with both compilers give the original's code with the struct and neither difference with the scalars).
- **The BWD keyword tag is an aggregate.** `StaticPoolAlloc` takes its size in `ecx` but its tag on the stack (`ret 4`), and `GetKeywordName` its tag on the stack too: under `/Gr` only a struct or union of 4 bytes is passed that way (a probe gives the callers' `mov eax, [tag]; mov ecx, size; push eax`). The tag is `BwdTag` (`bwdtag.h`), a structure of one `MechU32`: the nodes' types, `g_bwdTypeCodes`, the static pools' tags and the parameters that pass them, compared through `m_code`. `config.h` and `resourcename.h` declare it forward, which kept one of the headers' register-allocation shifts away.
- **Placement:** `vc22/targets.cmake` lists the units in the edition's object order, and `tools/check_units.py` passes with no known findings. Every game-code function has a MW23DFX annotation; what certify leaves unproven is classified by the audit or in `tools/known_diffs.txt`, register allocation and scheduling for most.

## The ATI edition (MW2ATI)

The ATI 3D Rage edition's simulator (`MW2_ATI.DLL`, linked 1996-04-11) is the oldest edition, five months before 1.1 and six before the 3Dfx edition (its registry key, `MechWarrior 2\1.0`, is the one 1.1 and the later editions kept). Its C already has what the later accelerated editions share, and the 3Dfx edition was built the same way six months later (VC++ 2.2, `/Ox /Ow /G5 /Gr /Gy`, 2.2's `LIBC`; the ATI edition has no Texus): 1186 of the 3Dfx edition's functions are byte-identical to the ATI edition's, relocations aside. Describe what they share in that order: the 3Dfx edition kept or changed the ATI edition's code ("Adding an edition", step 5, in `docs/EDITIONS.md`).

- **Annotations** were ported from the 3Dfx original by bytes (`tools/port_annotations.py --from MW23DFX MW2_3DFX.DLL --to MW2ATI MW2_ATI.DLL`). Relocations are masked, so a function or global the port places by bytes or pointers can be another one that differs only in what it addresses (the ATI edition's texture filter is at the place of the 3Dfx edition's 800x600 setting, its DirectDraw back end at that of the Glide one): datacmp and `tools/check_imports.py` find them. `tools/edition.py --target MW2ATI` pairs and counts like `--target MW23DFX`.
- **Back ends:** the display back end and refresh modes are DirectDraw's (`directdraw.c`, in the slot after `gdi.c` that the 3Dfx edition later fills with Glide's); the renderer, `MW2/src/ati/a3d.c` (`0x10063af0` to the import thunks), draws through ATI's 3D CIF (`3rdparty/ati3dcif`: our own declarations and the import library, checked against the SDK's `ATI3DCIF.H`), its vertex the CIF's `C3D_VTCF` (`A3DVertex` under `MW2_ATI`), its textures DirectDraw surfaces the CIF registers. Its texel copy is an `__asm` block (`tools/asm_allowlist.txt`). The client code is the interface the 3Dfx edition kept (`MW2_SKY_GROUND_CLIPPED_HELPERS`, `MW2_CLIP_TO_PANE_EDGES`, `MW2_FRAME_TEXELS`), with the edition's own `DrawAnimatedPolygon` and its textured-polygon drawer (`bandpoly.c`'s `FUN_1002a480`); `SimMain` and `SimWindowProc` are one definition for both editions. Its `SetGameResolution` asks DirectDraw for 512x384 (`MW2_RES_512X384`), and its VFX3D's first two routines are an older version than the release's, which the later editions link.
- **Features:** the 3Dfx edition kept its RGB555 pixels, inline helpers, map layouts, ranges, message backgrounds, near-plane clip and sky and ground clip; the Matrox edition kept its texture filter (which only the ATI edition lists on its graphics page, `MW2_TEXTURE_FILTER_ITEM`). Every site that tests `MW2_MATROX` or `MW2_3DFX`, and every feature no proven ATI function compiles, has been checked against it (`docs/EDITIONS.md`, "The ATI edition").
- **Placement:** the units are in the 3Dfx edition's order, and `tools/check_units.py` (`MW2ATI comdat`) passes with no findings. Its link drops unreferenced functions (`/OPT:REF`, which `/DEBUG` would otherwise turn off): the edition has none of 1.1's functions nothing calls (`GdiUpdateDibSection`, `PlayMidiSequence`, `GetCdAudioVolume`, `ToggleFullScreen`), which would otherwise bring in imports the original doesn't have.

## The S3 and PowerVR editions (MW2S3, MW2POWERVR)

The S3 ViRGE edition (`MW2_S3.DLL`, linked 1996-07-12) and the PowerVR edition (`MW2_POWERVR.DLL`, 1996-09-06) fall between the ATI and 3Dfx editions. Both started from the ATI edition (its features but its back end's, its client code for the renderer, its units' order), then took their own where their binaries differ.

- **Builds.** The PowerVR edition is the ATI edition's build (VC++ 2.2, LINK 2.55, `/QIfdiv` on; `vc22/targets.cmake`). The S3 edition is VC++ 4.1 with the same flags (its C runtime matches 4.1's `LIBC` as it is, and it has none of 2.2's division guards). Its sources' optimization flags are source properties, which CMake keeps per directory, so it is defined in `vc41/`, a directory of the top-level 4.1 build, where they don't reach MW2.DLL's `/Od` objects. Its `SimMain`'s `__finally` funclet, which 4.1 reaches with a `call` (and its scope table points to), is `SimMain`'s own code, not a function of its own in the traced count; so is the return address the PowerVR edition's `SimMain` pushes before its `__finally` block (2.2's `push`, block, `ret`).
- **The S3 edition** draws through S3's toolkit (`MW2/src/s3/a3d.c`, over `3rdparty/s3dtk`, checked against the toolkit's `S3DTK.H` of 1997): the ATI renderer's design (cached states, triangle fans, textures in DirectDraw surfaces with LRU reuse), its vertex the toolkit's `S3DTK_VERTEX_TEX`, its other calls through the renderer's function list. It links VFXA and the 16-bit port but neither VFX3D nor VFXREND (`MW2_NO_VFXREND`); its `directdraw.c` hands each unlocked frame to the renderer, and `ResetTicks` pops in its save order (`ticks.asm`). Its client code places polygons at the pane's origin with byte colours (`g_a3dPalette`), a layer of its own in `polydraw.c`, `cockpit.c` and `animation.c`. `bandtexture.c` is its copy of the ATI edition's textured-polygon drawer, which opens `palette.c`'s object: including a fragment of `bandpoly.c` instead changed `DrawBand` in the 2.2 editions (next item).
- **The PowerVR edition** draws through VideoLogic's SGL scene graph (`MW2/src/powervr/a3d.c`, over `3rdparty/sgl`): the models are SGL meshes, the objects SGL lists with transforms, the animation frames cached textures, in three views (the 3D view and two cockpit panels' insets). SGL owns DirectDraw (`directdraw.c` has no surfaces of its own) and calls the game back with the locked frame, where `FUN_10007db0` (`simmain.c`) draws the cockpit, the menus and the overlays. Its graphics page has fog and smooth shading; the PowerVR members of `Animation`, `AnimFrame`, `SceneObject`, `Shape` and `Model` hold the SGL objects.
- **Annotations** were ported by bytes from the ATI and 3Dfx originals, the C runtime from the rebuilds (`tools/port_annotations.py --rebuild`), the rest paired with `tools/edition.py --target MW2S3` / `MW2POWERVR`. The cautions of the ATI edition's port apply.
- **Checks:** `tools/check_units.py` and `tools/check_imports.py` pass for both; their links drop unreferenced functions (`/OPT:REF`), as the ATI edition's do. So a function the original calls but the source doesn't call yet is left out of the link, and reccmp reports it missing ("Failed to find function symbol"): the caller's source isn't the edition's yet.

## The GBL edition (MW2GBL)

Ghost Bear's Legacy's simulator (`MW2_GBL.DLL`: the `MW2.DLL` of the expansion's 1.1 patch, `GBLPATCH.EXE`, the same file as the GBL disc's `MW2.DLL`) was linked on 1996-10-18 by LINK 3.10, four weeks after 1.1, from 1.1's code: most of its functions are 1.1's byte for byte, relocations aside. CI fetches it with the 1.1 patch (`.github/workflows/mw2bin.yml`: the same ARJ archive at `0x1853`), so it is a public target.

- **Build:** VC++ 4.1, `/Od /G5`, 4.1's `LIBCMTD` (`/MTd`), like 1.1 but without `/Oi` (the target's `DEMECH2_NO_INTRINSICS`: `/Oi` is a compile option of `cmake/decomp_flags.cmake`): it calls `memcpy`, `memset`, `strcmp`, `memcmp` and the math functions where 1.1 expands them or calls their `__CI` entries. It expands `abs` and `fabs` all the same; how isn't known, and `util/types.h` reproduces it (`#pragma intrinsic(abs, fabs)` under `MW2_GBL`, after the CRT's prototypes: 4.1 takes the pragma only for a function already declared). It was linked without `/DEBUG` (no debug directory), so with `/OPT:REF`: it has none of the functions nothing calls, nor the imports of the C runtime they bring in (1.1's `HeapWalk`, locale and console imports); the comparison build passes `/OPT:REF` with its `/DEBUG`. The target is defined in the top-level `CMakeLists.txt`, with `MW2_GBL` (and not `MW2_ACCEL`), its units in its own order (`MW2/sources_gbl.cmake`).
- **Placement:** `MW2/sources_gbl.cmake` lists the units in its object order, and `tools/check_units.py` passes. Its cockpit panels, its faces' projection and `clock.c`'s tables are objects of their own, which it builds from 1.1's fragments (`cockpitpanels.c`, `faceprojection.c`, `clockmath.c`); `refreshmode.c` defines three of `simmain.c`'s globals for it (`g_desktopWidth`…), and `ai.h` annotates `RunAIRules` by name (GBL places it after `FirstAI`).
- **Annotations** come from `tools/port_annotations.py`, by bytes from 1.1's original, then from the rebuild (`--rebuild`, `--after MW2`). Every function is byte-identical or proven by a witness, with no line in `tools/known_diffs.txt`.
- **Structures:** `Mech` and `Player` have GBL's members behind its features (`MW2_EXTERNAL_HEAT`, `MW2_MECH_SECOND_FLAGS`, `MW2_PILOT_TABLE`, `MW2_AI_FLAGS_INT`), their headers saying how far GBL's members sit from the offsets the comments give; a mech has `WEAPON_SLOT_COUNT` (14 in GBL) weapon slots.
- **Data:** 14 weapon panels (the panel enum and `cockpitpanels.c`'s `FIRST_RIGHT_WEAPON_PANEL`/`LAST_WEAPON_PANEL` follow `WEAPON_SLOT_COUNT`, and its panel tables have 30 entries); two game keys of its own (`GAME_KEY_ACTION` numbers an action past GBL's `CHAT_MODE`, in `util/types.h` because `inputmap.c` and `settings.c` share no other header); its titles, CD driver and local star behind features; VFX as released for VFXA (`MW2_VFX_STOCK`, `MW2_VFX_LOOKASIDE_WRITE`) but 1.1's VFX3D fill (`MW2_VFX3D_ALIGNED_FILL`), the target passing ML its features. Its weapons, shots and effects are `MW2_WEAPON_FUNCTIONS` (`docs/EDITIONS.md`): each weapon type has a frame and a launch function, flags and an animation (35 types), and the shots, effects and effect types are larger and more (`SHOT_COUNT`, `EFFECT_COUNT`, `EFFECT_TYPE_COUNT`); the AMS's object is `MW2/src/gbl/ams.c`, linked before `refreshmode.c`. Its maneuver tables are data (`MW2_STATIC_MANEUVER_TABLES`), with the pilot table's in `ai.c`. Every function of its game code is annotated, and every global 1.1 has that GBL compiles, but two 1.1 placeholders nothing references.
- **What it changed** besides: its cheat codes are a table (`g_cheatCodes`, `MW2_CHEAT_TABLE`: codes and messages XORed with 0xa, the messages decoded at the first key, codes of its own); `RunGameKey` and `HandleDebugKey` number their keys with `GAME_KEY_ACTION` and take the chat, AMS and PT menu keys; `GetIniValue` cuts comments (`MW2_INI_COMMENTS`; error.c's call passes only the key, so the header declares it without parameters); more structure copies are `memcpy` calls (`MW2_STRUCT_COPY_MEMCPY`). Its objectives are 1.1's with the Matrox edition's leader test and the 3D-card editions' network stars, and a lost local mech fails the local star. Its DirectDraw back end is 1.1's built with DirectX 1's `DDCAPS` (`MW2_DDRAW_CAPS_DX1`, `MW2_DDRAW_STOP_KEEPS_MODE`), and another machine's mech stays where it is (`MW2_REMOTE_MECHS_STAY`). `docs/EDITIONS.md` describes the rest; three functions take a GBL-only declaration order (`#ifdef MW2_GBL` around their locals), where the order its code needs would cost another edition its proof.

## The early Mercenaries build (MW2PREMERCS)

An unused early build of Mercenaries' simulator, left as `/MERCS/MW2.DLL` on the Mercenaries discs (`MW2_PREMERCS.DLL`, linked 1996-07-08 by LINK 3.10), is Ghost Bear's Legacy's code, three months before GBL's patch; `docs/EDITIONS.md` describes it. It is a retail target: CI reads it from the private repository with the other retail originals.

- **Build:** as GBL's (VC++ 4.1, `/Od /G5`, `LIBCMTD`, no `/Oi`, `abs` and `fabs` expanded by `util/types.h`'s pragma), but linked with `/DEBUG /INCREMENTAL:no` and so without `/OPT:REF`, as 1.1: the original has a debug directory and 1.1's C runtime imports. The target is defined in the top-level `CMakeLists.txt` with `MW2_PREMERCS`, linked from `o\p\` (LINK 3.10's response file, as GBL's `o\g\`).
- **Starting point:** `MW2_PREMERCS` has every feature of `MW2_GBL` in `util/types.h`, and `MW2_JOYSTICK_OPEN_POSEX`, `MW2_SHAPE_GRID`, `MW2_PLAYER_UNK_MEMBERS`, `MW2_MECH_UNK_MEMBERS`, `MW2_COCKPIT_PANEL_UNK_MEMBERS`, `MW2_CLAN_AND_IS_WEAPONS` and `MW2_SHOT_TRACERS`, which GBL lacks, and lacks GBL's `MW2_AMS_CHECKS_BIN`, and the target builds GBL's units in its own order (`MW2/sources_premercs.cmake`, which `tools/check_units.py` checks as for the other targets): it has GBL's fragments as units too, so the sites that place them (`clock.c`, `config.c`, `objectanim.c`, `refreshmode.c`, `simmain.c`) take GBL's branch for it. GBL's three declaration-order sites (`#ifdef MW2_GBL` in `mechcollision.c`, `quadtree.c`, `weapons.c`) don't: nothing shows which order it needs yet. What it doesn't share with GBL is the next step: each GBL feature it lacks leaves its block, each it has moves to one both identities select.
- **Annotations:** ported from GBL's original, then from 1.1's for what GBL lacks (`tools/port_annotations.py --from MW2GBL MW2_GBL.DLL --to MW2PREMERCS MW2_PREMERCS.DLL`, then `--from MW2 MW2.DLL`). Two ports leave two markers for the target in a block where both match, and the second can land out of order: keep one per block, GBL's where they disagree, in `targets.toml`'s order. What certify leaves unproven after the witness search, and the globals datacmp reports, were left out; port again from the rebuild (`--rebuild`, `--after MW2 MW2GBL`).
